# 路线图

## 1. 当前阶段定位

本项目目前处于**纯设计概念阶段**。

已完成的内容：
- 愿景与问题定义
- 核心机制框架（双轨胜利 + Ruin 系统）
- 排名、评分与反摆烂思路
- 英雄与装备方向
- 观赏性与电竞叙事考量
- 主要平衡风险与边界情况梳理

尚未完成、也尚未验证的内容：
- 任何可运行的原型
- 具体数值与公式
- 真实玩家测试数据
- 完整的英雄/装备案例

因此，当前最重要的目标不是「尽快做成游戏」，而是把设计概念打磨到足够清晰、经得起质疑的程度。

## 2. 阶段划分

### 阶段 0：设计完善与公开讨论（当前）

**目标**  
让核心逻辑经得起外部审视，暴露尽可能多的问题。

**主要工作**  
- 持续完善现有文档
- 针对高风险问题（价值死亡识别、触发强度、反制手段）进行深入讨论
- 收集外部反馈与反驳意见
- 明确哪些问题必须在进入原型前解决

**完成标准**  
- 主要设计文档不再有明显逻辑漏洞
- 对核心风险有至少一种可讨论的应对思路
- 形成一个相对稳定的「当前共识版本」

### 阶段 1：低成本验证（纸面 / 表格 / 规则模拟）

**目标**  
用最低成本验证「价值死亡」和「路径选择」是否具备基本可玩性。

**可能方式**  
- 纸面推演或表格模拟几场完整对局
- 用现有 MOBA 自定义房间 + 人工记录 Ruin 的方式进行小范围测试
- 针对单一机制（例如「如何判断一次死亡有价值」）做专项规则实验

**完成标准**  
- 能跑通至少数局完整的双路径对局流程
- 对「什么算高价值死亡」形成可操作的判断标准
- 发现并记录新的边界情况

### 阶段 2：最小可玩原型（Greybox Prototype）

**目标**  
做出一个能让人实际操作、感受节奏的简化版本。

**可能技术路径**  
- 使用 Godot / Unity 制作极简 5v5 或更小规模原型
- 或深度魔改现有开源/可模组化的 MOBA 项目
- 重点实现：Ruin 获取、触发、基础反馈，而非精美美术或完整英雄池

**完成标准**  
- 玩家可以在不看文档的情况下，通过游戏内反馈理解基本规则
- 能收集到关于节奏、强度、理解成本的第一手感受
- 确认「是否值得继续投入」的判断依据

### 阶段 3：公开测试与迭代

**目标**  
让真实玩家接触系统，观察实际行为与反馈。

**主要工作**  
- 小范围封闭测试 → 扩大测试
- 重点观察：假摔发生率、对局时长变化、路径选择比例、玩家理解速度
- 根据数据与反馈回头修正机制和数值

**完成标准**  
- 假摔行为被有效抑制
- 崩坏路径在一定水平的玩家中成为「可选策略」而非「必选」或「无人问津」
- 观赛理解成本在可接受范围内

### 阶段 4：长期可能性（暂不承诺）

只有在阶段 3 取得积极结果后，才考虑以下方向：
- 是否值得做成独立模式或完整游戏
- 是否寻求与现有游戏的合作/模组形式落地
- 是否进一步扩展为更完整的设计文档或商业提案

在此之前，不做任何商业或完整产品化的承诺。

## 3. 优先级原则

1. **先解决会让系统崩溃的问题**（假摔、触发失控、节奏破坏）
2. **再优化体验与深度**（英雄差异、叙事、微调）
3. **最后才考虑表达与包装**（美术、完整英雄、商业化）

## 4. 明确不做什么（当前阶段）

- 不追求快速做出可上线的完整游戏
- 不提前进行大规模宣传或社区运营
- 不把「有人觉得有趣」等同于「机制已经成立」
- 不回避尖锐的否定意见

## 5. 参与方式建议

- 发现文档中的逻辑问题或遗漏 → 直接提 Issue
- 对某个具体风险有更好的解决思路 → 开 Discussion 或 PR
- 愿意参与纸面推演或早期测试 → 在 Issue 中表明意向

所有贡献以把设计推得更严谨为优先，而不是追求表面完整。

## 6. 总结

当前最有价值的工作，是继续把这个概念放在聚光灯下审视。  

只有当它能经受住足够多的质疑，并且核心风险有了可信的应对方式之后，进入原型阶段才有意义。  

路线图会随着实际进展更新。
